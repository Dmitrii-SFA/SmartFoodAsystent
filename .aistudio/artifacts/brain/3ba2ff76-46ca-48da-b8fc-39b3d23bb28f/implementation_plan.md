# План: Надёжное суммирование остатка AI-запросов при активации купленного ключа (`500 + остаток`)

## 1. Как сейчас устроено хранение баланса и почему важно защитить все точки перехода

В приложении баланс оставшихся AI-запросов хранится и синхронизируется на двух уровнях:

1. **На стороне приложения (локальное хранилище браузера / PWA)**:
   - Хранит остаток стартового бесплатного пакета (из начальных `100` запросов).
   - Хранит таблицу балансов и лимитов для каждого активированного платного ключа.
   - Определяет активный баланс, который пользователь видит в шапке приложения и в модальном окне AI-доступа.
2. **На стороне сервера Cloudflare (`USERS_KV`)**:
   - Для каждого платного ключа в базе `USERS_KV` хранится JSON-запись с полями:
     - `remaining` — сколько запросов осталось у этого ключа;
     - `initialLimit` — общий размер пакета с учётом перенесённого остатка (например, `533`);
     - `devices` — список привязанных устройств (до 2 устройств);
     - `carryoverApplied` — флаг, гарантирующий, что перенос старого остатка на этот новый ключ выполнится ровно один раз (при первой активации), а на втором устройстве просто подтянется уже готовый единый баланс `533`.

```
[ Приложение: Текущий баланс = 33 ]
        │
        ▼  Пользователь покупает пакет (500) и вводит новый ключ
[ Запрос активации (verifyKeyOnly) ]
  Передаёт:
  • accessKey (новый ключ)
  • previousAccessKey (прежний ключ, если был)
  • carryoverRequests = 33 (точный текущий остаток в приложении)
        │
        ▼
[ Cloudflare Worker + USERS_KV ]
  1. Проверяет, что новый ключ валиден и активируется впервые (!carryoverApplied)
  2. Вычисляет бонус переноса:
     максимум из (остаток в приложении = 33, остаток старого ключа в KV)
  3. Записывает для нового ключа в USERS_KV:
     • remaining = 500 + 33 = 533
     • initialLimit = 533
     • carryoverApplied = true
  4. Обнуляет старый ключ в USERS_KV (remaining = 0), чтобы остаток не начислился дважды
        │
        ▼
[ Приложение получает ответ: remainingRequests = 533, packageLimit = 533 ]
  • Сохраняет 533 как баланс нового ключа
  • Обнуляет локальный стартовый/старый остаток
  • При последующих AI-запросах списывает по 1 (532, 531...) без сброса до 500
```

## 2. Что именно мы исправим и укрепим, чтобы баланс никогда не затирался

В ходе проверки кода обнаружены 4 узких места, из-за которых при определённых сценариях число `500` могло перезаписать старый остаток вместо сложения. Мы устраним каждое из них:

### А. Исправление потери остатка при переходе по ссылке с ключом (`?key=...`)
- **В чём была проблема**: При открытии приложения по ссылке с параметром `?key=...` функция автоактивации сначала сохраняла новый ключ поверх старого со стандартным балансом `500`, и только потом вызывала проверку на сервере. В результате к моменту расчёта переноса приложение считало, что этот ключ уже активен, и переносимый остаток становился равен `0`.
- **Как исправим**: Считывание текущего остатка (`carryoverRequests`) и передача его на сервер будут происходить **строго до** перезаписи активного ключа в памяти приложения.

### Б. Приоритет максимального фактического остатка на сервере Cloudflare
- **В чём была проблема**: Если у пользователя раньше уже был платный ключ, воркер на сервере смотрел только на запись старого ключа в `USERS_KV`. Если по какой-то причине старый ключ не был записан в `USERS_KV` (например, использовался до подключения KV или в локальном режиме), сервер брал `0` вместо фактического остатка `33`, который передало приложение.
- **Как исправим**: При первой активации нового ключа сервер будет брать `Math.max(остаток_старого_ключа_в_KV, остаток_переданный_приложением)` (ограниченный разумным лимитом, чтобы исключить некорректные данные) и прибавлять его к `500`. Таким образом, и остаток от стартовых `100` запросов, и остаток от предыдущего ключа гарантированно прибавятся к `500`.

### В. Защита от перезаписи баланса при первом реальном AI-запросе
- **В чём была проблема**: Если ключ был активирован, когда сервер работал в резервном режиме (или не вернул поле `carryoverAdded`), либо если пользователь сразу отправил AI-запрос, следующий ответ сервера мог вернуть стандартные `499` вместо `532` (`533 - 1`).
- **Как исправим**:
  - На клиенте: при активации нового ключа, если локально был ненулевой остаток (например, `33`), а сервер не подтвердил его включение в `remainingRequests`, клиент сохранит `500 + 33 = 533` и передаст этот остаток при следующем AI-запросе.
  - На сервере: даже если первый запрос с новым ключом пришёл сразу как обычный AI-запрос (а не только через кнопку «Проверить и сохранить»), сервер точно так же проверит флаг `!record.carryoverApplied`, прибавит переданный `carryoverRequests` (`500 + 33 - 1 = 532`), сохранит `initialLimit = 533` и вернёт правильный суммарный остаток.

### Г. Наглядный расчёт сложения в окне ввода ключа
- В модальном окне управления AI-доступом (где пользователь вводит купленный ключ):
  - **До ввода нового ключа** (если у пользователя есть текущий остаток > 0, например `33`): отобразим понятную подсказку-расчёт: *«При активации нового ключа ваш текущий остаток (33) прибавится к 500 запросам → итого будет 533 запроса»* (на языке интерфейса: EN / RU / PL).
  - **Сразу после активации**: покажем уведомление с точным итогом: *«Ключ активирован! К 500 запросам прибавлен ваш остаток (+33). Итого доступно: 533»*.

## 3. Нужно ли что-то менять вручную в панели Cloudflare?

**Вручную в панели Cloudflare ничего менять не нужно**, так как:
1. Вы обновляете код через **GitHub с автоматическим деплоем в Cloudflare**.
2. Привязка базы `USERS_KV` (`id: f88a2d8d574b41f59e6db567479fb7db`) уже прописана в конфигурации проекта.
3. Мы синхронно обновим серверную логику во всех трёх серверных обработчиках проекта (основной Cloudflare Worker, Cloudflare Pages Function и локальный сервер разработки).

**Что потребуется от вас после того, как мы внесём изменения в код:**
1. Просто отправить обновлённый код в ваш GitHub-репозиторий (обычный `git push` / экспорт в GitHub).
2. Cloudflare автоматически соберёт и задеплоит обновлённый воркер.
3. При генерации новых ключей для покупателей просто добавляйте новый ключ в переменную `ALLOWED_KEYS` (как вы делаете сейчас) — при первом вводе этого ключа покупателем воркер автоматически создаст запись в `USERS_KV` со значением `500 + текущий_остаток_пользователя`.
